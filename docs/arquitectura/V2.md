# Portal RYM - Arquitectura V2

## Objetivo

Aislar Panapass, GPS, Revisados, Control de Auto y Usuarios para que un cambio de UI, estado o logica en un dominio no produzca regresiones en otro.

## Principios obligatorios

1. Un modulo puede depender de `modules/core/`, pero no de otro modulo de negocio.
2. Ningun codigo nuevo de modulo debe leer directamente `window.state`, `window.rpc` ni entrypoints legacy globales.
3. Los servicios compartidos se reciben a traves de `RYM_CONTEXT`.
4. La comunicacion entre modulos se hace mediante eventos, nunca mediante llamadas directas.
5. Cada modulo debe soportar ciclo de vida `mount` / `unmount`.
6. El CSS de un modulo debe quedar namespaced y evolucionar hacia aislamiento de DOM/Shadow DOM.
7. `main` no recibe esta migracion hasta que el piloto pase QA funcional y visual.

## Core V2

- `modules/core/event-bus.js`: eventos desacoplados.
- `modules/core/context.js`: contrato de servicios para los modulos.
- `modules/core/module-registry.js`: registro y apertura de modulos.

El contexto expone inicialmente:

- `session`
- `api`
- `events`
- `router`
- `root`

La implementacion inicial contiene adaptadores legacy para permitir una migracion progresiva sin cambiar reglas de negocio.

## Contrato de modulo

Cada modulo nuevo debe exponer conceptualmente:

```js
{
  init(context),
  open(context),
  mount(context),
  unmount()
}
```

`open` existe por compatibilidad con V171. La meta es que `mount/unmount` sea el contrato canonico.

## Fronteras

Permitido:

```text
modules/panapass -> modules/core
modules/gps -> modules/core
modules/revisados -> modules/core
modules/control-auto -> modules/core
modules/usuarios -> modules/core
```

Prohibido:

```text
modules/panapass -> modules/gps
modules/gps -> modules/panapass
modules/revisados -> modules/control-auto
... cualquier dependencia directa entre dominios
```

## Estrategia de migracion

### Fase 1 - Boundary

Panapass deja de llamar legacy directamente y entra por `RYM_CONTEXT`.

### Fase 2 - API

Mover RPC y Edge Functions usadas por Panapass a una API de dominio estable (`context.api.panapass`).

### Fase 3 - Estado

Eliminar lecturas de `window.state` dentro de Panapass. El modulo recibe `context.session` y mantiene su propio estado local.

### Fase 4 - DOM y CSS

Encapsular componentes de Panapass y evitar selectores globales. Preparar Custom Elements / Shadow DOM para las vistas de mayor riesgo.

### Fase 5 - QA

Agregar pruebas que abran/cambien/cierre Panapass y verifiquen que GPS, Revisados y Control de Auto mantienen entrypoints, DOM y comportamiento esperado.

### Fase 6 - Replicacion

Aplicar el mismo patron a GPS, Revisados, Control de Auto y Usuarios.

## CI

El workflow `.github/workflows/architecture-v2-contracts.yml` valida la rama piloto y debe fallar ante:

- errores de sintaxis del core o boundary;
- Panapass llamando directamente al entrypoint legacy;
- dependencias Panapass <-> GPS;
- ausencia de `RYM_CONTEXT`;
- ausencia de `mount/unmount`;
- ausencia de eventos del ciclo de vida.

## Estado actual del piloto

Rama: `architecture-v2-panapass-pilot`.

La rama no despliega a produccion. El primer boundary de Panapass ya consume `RYM_CONTEXT`; la llamada legacy permanece temporalmente encapsulada dentro del adaptador de core para evitar cambiar reglas funcionales durante esta primera fase.
